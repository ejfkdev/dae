# 反编译质量基线

`--decompile` 的产物是**伪代码，同时也是合法 Dart**：能解析，能过 `dart analyze` 且零错误。
这就是验收线——它是唯一不依赖我们自己"看着还行"的判据：真正的前端得点头。

英文版：[`DECOMPILER.md`](DECOMPILER.md)。

## 判据怎么跑

两条检查，签出即可复现：

```bash
cargo test --release --test dart_valid              # 门禁：每个可用语料都要求 0 错误
cargo test --release --test dart_valid -- --ignored --nocapture   # 全量基线（25 个 SDK 产物）
cargo test --release --test decompiler_shape       # 形态门禁 + 地址自洽性门禁
cargo test --release --test field_names            # 字段名恢复：两源一致 + 零冲突
cargo test --release --test source_truth           # 现编 tests/fixtures/truth.dart，反编译后对源码判
DAE_TRUTH_ANDROID=1 cargo test --release --test source_truth   # 同一套判据跑压缩指针 arm64 产物
DAE_REQUIRE_GATES=1 cargo test --release           # 把所有「缺依赖，跳过」变成失败
```

最后这条比看上去要紧。6 个门禁文件里有 5 个要吃被 gitignore 的语料（`testing/`、
`dart/dart_samples/`），缺了就自行跳过，而 `cargo test` 默认把提示吞掉——于是新克隆会报告
「套件全绿」而实际几乎什么都没量。`DAE_REQUIRE_GATES=1` 让这类跳过直接失败，
这是区分「门禁通过了」与「门禁根本没跑」的唯一办法。

`tests/source_truth.rs` 是唯一**输入是源码**的门禁：用本机 `dart` 编 `tests/fixtures/truth.dart`，
反编译后断言源码说必须留下来的东西——快照里归属该库的每个函数都渲染出来、`main` 会走到的字符串常量
被内联、`Account.withdraw` 保留 `-1` 分支与比较（未被内联时）、产物零 `dart analyze` 错误、解析不漂移。
安卓变体对 `flutter assemble` 现编的 arm64 **压缩指针**产物跑同一套判据（刻意绕开 Gradle：
它首跑会长时间卡在依赖下载上）。

**门禁要能自证。** 一个「什么都没量到也能通过」的门禁比没有门禁更坏——这个仓库为此付过两次学费
（序言率检查替掉了「末指令是终止符」检查，后者在地址全错时照样 95.7%，因为它在数 x64 的 `int3` 填充）。
所以两个 `dart analyze` 门禁都会拿**工具自己的退出码与总结行**（`No issues found!` / `N issues found.`）
反查自己的解析结果：rc=0/1/2 必须解析出 0 个 error、rc=3 必须解析出至少 1 个，且总结行必须出现。
`dart analyze` 指向不存在的目录时返回 rc=64 + usage 文本，里面一条 `error - ` 都没有，
旧解析器把它读成「0 错误」——对一份根本没被分析过的产物盖了通过章。现在每个门禁都带一条
`*_rejects_directory_it_never_analyzed` 自检测试，那个洞一回来就失败；`dart_valid` 还额外断言
每个语料都真的产出了文件与函数，于是「产物为空」再也不能冒充「产物干净」。

`tests/dart_valid.rs` 对产物目录调 `dart analyze`，只数 `error -` 行：警告与提示（未使用变量、
未使用 import）不计——它们不影响"能不能编译"。`dart` 不在 `PATH` 时整条测试自动跳过，
所以在没有 Dart SDK 的机器上不会变成红。

为了"合法 Dart"，一共要处理这些（都在 `src/decompiler.rs`）：

- **机器语法不是 Dart**：`[x2, #0x3f]`、`#0x30`、`qword ptr`、`v2.2d`、`goto L40a8;`、
  `call foo`、`a, b = mem(...)` 全是解析错误。内存改成 `mem(base, disp)` / `memSet(base, disp, value)`，
  间接调用 `callIndirect(x8)`，无法结构化的跳转 `gotoLabel(0x..)`，SIMD 车道 `v2_2d`。
- **名字必须是标识符**：mixin application 的类名带 `&`（`Set&_LinkedHashBase&…`），而 `&` 在 Dart 里
  是运算符；保留字（`rethrow`）与伪运行时占位名（`toDouble`）要改名；同一文件里算出同名的
  两个入口加 `_2`/`_3`。
- **每个文件一段"伪运行时"前导**：声明机器层概念（`mem`/`memSet`/`memRead2`/`callIndirect`/
  `gotoLabel`/`addr`/`abort`/…）以及正文用到但本文件没定义的名字（寄存器、跨库调用目标）。
  这不是"假装编译得过"——它把「机器层到哪里为止、Dart 语义从哪里开始」显式写了出来。

修的过程（按 `dart analyze` 报出来的顺序；数字取自真实 Flutter 应用：412 个文件、
10 245 个函数）：

| 阶段 | `error -` 条数 | 主因 |
|---|---|---|
| 首次测量 | 680,515 | 表达式里带 `[..]`/`#`/`goto`/`call` |
| 内存/调用/跳转改写 | 40,347 | 寄存器与函数未声明 |
| 前导声明 + 文件内改名 | 7,950 | `mem(mem(..))` 套娃、`v2.2d` 声明 |
| 寻址修饰 + x86 尺寸前缀 | 1,800 | `qword ptr` 里含 `word ptr`、`ds:` |
| 条件与 `Node::Line` 兜底清洗 | 4 | `if (…)` 里的 `qword ptr [..]` |
| 保留字 / `print` / 成对写栈槽 | **0** | — |

## 性能

`DART_AOT_PROF=1` 会打印 `render` 的分阶段耗时。加它是因为 release 开了 LTO，调用树被内联打散，
`sample` 把约 86% 归给 `start`、dae 自身符号最高才 0.6%——照着那个猜，先后做出两处
「输出一致但无可测收益」的改动，最后是靠计时才找到真因。

`material_3_demo`（15 082 个函数、985 900 条语句）与真机产物：

| 产物 | 之前 | 之后 | 产物 |
|---|---|---|---|
| `material_3_demo` | 113.5 s、峰值 236 MB | **3.4 s、217 MB** | 逐字节一致 |
| 飞书 3.6.1（安卓） | 181.3 s | **1.6 s** | 指标一致、analyze 0 错误 |
| Reqable.app 3.3.4（macOS） | 156.0 s | **1.0 s** | 指标一致、analyze 0 错误 |
| 微博 2.19.6（安卓） | ~214 s | **5.6 s** | 指标一致 |

病因是两处**每函数重建一次的全局不变数据**：`lift` 自己调 `roles(analyzer)`，而 `roles` 会构建
整张对象池映射（`BTreeMap<u64, String>`，Reqable.app 有 122 064 条）；`Structurer` 又按值持有
`Roles`，于是 `emit_function` 每个函数都深拷贝一遍同一张表。两处都改成借用。修复后各阶段：
lift 1.91 s（66.8%）、emit 0.71 s（25.0%）、前导 0.14 s、CFG 0.03 s。

这也推翻了本文档早先「`--decompile` 的时间主要花在约 100 万次 `format!`」的说法：渲染只占
render 的 5.7%；剖析里那些分配密集的叶子是**池表被反复重建**，不是语句格式化。

### 第二轮：寄存器别名表

lift 仍占 66.8%，下一个逐指令开销是 `mask_regs`——它改写 capstone 的操作数文本
（`x15` → `SP`、`x27` → `PP`）。它**每次调用都重建别名表**：克隆 profile 的 `register_aliases`、
追加 `pp`/`thr` 与九个硬编码项、按 key 长度降序做稳定排序，然后每个 pair 各跑一次
`replace_word`——而每次 `replace_word` 都分配一个新 `String` 并把整段文本重扫一遍。约 100 万条
指令 × 20 个 pair = 两千万次分配与两千万次全文扫描。这张表对整个 run 是不变量，所以现在只在
`roles` 里建一次，`mask_regs` 变成单遍：按 `replace_word` 用的同一个 `[A-Za-z0-9_]` 词边界切
token、查表、分隔符整段拷贝。

单遍查表**并不**天然等价于顺序替换，因为替换会级联。arm64 profile 把 `x29` → `fp`、`x30` → `lr`
（小写），硬编码表尾再 `fp` → `FP`、`lr` → `LR`；按长度降序稳定排序后三字符键先跑，所以 `x29`
最终是以 `FP` 而不是 `fp` 进入产物。因此 `build_mask_map` 是**按原有 pair 顺序模拟整条链**来解析
每个键，而不是做图可达性——可达性会把「值等于某个**更早**的键」也算进去，而顺序替换从不回头再
应用它。`xzr` → `xzr` 这类自映射也自然落对。

| 产物 | 第一轮 | 第二轮 | 产物 |
|---|---|---|---|
| `material_3_demo` | 3.4 s、217 MB | **2.1 s、188 MB** | 逐字节一致 |
| ↳ `lift` 阶段 | 1.95 s（66.7%） | **0.63 s（40.3%）** | 3.1× |
| ↳ `emit_function` | 0.73 s | 0.71 s | 不变（不在这条路径上） |
| 飞书 8.0.2（安卓 arm64） | 1.56 s、174 MB | **1.41 s、167 MB** | 逐字节一致 |

计时是三轮交错 A/B（3.51/3.67/3.45 → 2.08/2.29/2.13 s）；同一二进制在主机有无关负载时会飘约
35%，所以单次跑数不算证据。字节一致用 `diff -rq` 对整棵产物树验过：`material_3_demo`、飞书，
以及五个语料变体（覆盖 Mach-O x64、ELF x64、ELF arm64 与 SDK 2.10/2.14）——**只测 arm64 语料
不会走到 x64 的别名表**。每一项的指标都逐项相同（181 504 块 / 985 900 语句 / 13 950 结构化 /
1 132 未结构化 / 3 行 unmapped）。

已发布 v0.1.8 二进制上的**当前绝对值**（给想知道「现在到底多快」而不是分轮增量的读者；
主机负载 13–20，来自无关进程，所以这些数字当上界看）：飞书 3.6.1 安卓、25.6 MB、25 183 个表项函数
——`--decompile` **1.63 s**；微博 2.19.6 安卓、9 MB、19 053 个反编译函数 / 153 万条语句——**3.51 s**；
`material_3_demo` macOS、14 MB、15 796 个函数——**2.37 s**；不带 `--decompile` 的纯导出，
9 MB 样本 0.26 s、飞书 0.96 s。上面第一轮表里微博仍写 5.6 s，那是它**第一轮**的测量值，
第二三轮把它带到了 3.5 s。

本轮还包含：八处 capstone 引擎构造从 `.detail(true)` 改成 `.detail(false)`。grep 确认全仓没有
任何 detail API 被用到（只用 `mnemonic`、`op_str`、`address`、`bytes`），所以这是**严格更少的
工作量**，但 A/B **测不出加速**（差异落在主机噪声内）。保留它的理由是「不会更差」，上面那些
数字里不含它的贡献。

### 第三轮：内存，以及它到底在哪

峰值 RSS 是**量出来**的，不是猜的；路上死了两个假设：

- `dae info`（只解析）峰值 **41 MB**，完整导出 **151 MB**。所以内存问题**不在反编译器**——
  解析很便宜，是导出管线持有约 110 MB。
- 用 `--no-default-features` 构建（去掉 `asm` + `callgraph`）峰值 **60 MB**，
  这两个导出器占了峰值里约 91 MB。
- 最像嫌疑犯的那个是错的：`asm` 每文件一个 `String::with_capacity(job.est)`、最多 8 线程在飞，
  但最大单文件只有 1.3 MB，并发缓冲上限约 10 MB——不是大头。

八个导出器实际是**并发**跑的（`std::thread::scope`，各一线程），所以峰值是它们工作集之和，
这也解释了导出期间 RSS 为何单调爬升、从不回落。

`callgraph` 里有一个真缺陷：边是用
`sort_by_key(|a| (a.from, a.to, a.to_text.clone()))` 排的。**`sort_by_key` 不缓存键**——每次比较
都重调一次闭包——于是每次比较都分配一个 `String`：96 904 条边 × O(log N) ≈ **160 万次克隆**，
更大的应用按比例更多。现在改成借用键排序（`to_text.as_str()`），序完全相同（`String` 与 `str`
都是逐字节字典序）、同样是稳定排序。合并各线程分片时也一次性预留总长，不再让一个约 14 MB 的
`Vec` 反复翻倍。

| 模式 | HEAD | 第二+三轮后 | 产物 |
|---|---|---|---|
| 仅导出 | 169/164/175 MB、约 0.48 s | **138/140/149 MB、约 0.48 s** | 逐字节一致（506 文件） |
| `--decompile` | 220/223/212 MB、3.89/4.22/3.52 s | **180/180/173 MB、2.55/2.08/2.31 s** | 逐字节一致 |

各三轮交错，主机负载约 7.5——绝对值偏高，但配对是公平的。注意这里**没有**声称的事：
callgraph 那一改买到的是内存与消除 160 万次分配，导出墙钟并没有可测变化（排 9.6 万条边本来就快）。

字节一致用 `diff -rq` 对整棵树复验过：`material_3_demo` **两种模式**、飞书、以及五个语料变体；
`call_edges.txt` 逐行相同（96 904 / 12 011 行），这正是新比较器排序一致的直接证据。
记一个假警报：有一次 `diff -rq z_old z_new` 用了相对路径、而 cwd 不对，报出的「差异」其实只是
diff 找不到目录的退出码 2。可靠做法是用绝对路径，并确认 `diff` **没有输出**。

## 这张表反复踩的同一个坑

同一个失效模式已经出现三次，值得直说——**指标看不见它**：指令段定位错了，反编译器读的是
**别的字节**。函数名、结构化率、能不能过分析全都照旧正常（名字来自 Code 对象，合法性只关乎语法）。
唯一能暴露它的是**地址自洽性**（判据：入口像不像序言、直接调用是否落在函数入口上）。

- arm64 `dart compile exe`（尾部内嵌 Mach-O，无符号）——`instr_off = 0`；
- x64 2.12–2.14 / 3.3.4 `dart compile exe`——快照是**另一个 ELF 容器**贴在文件尾部，靠文件末尾
  trailer（`[offset][kAppJITMagicNumber]`）寻址；只看可执行文件自身的符号表就漏了。
  修好之后 `hello_2.13.4` 那 1394 个共同函数的地址**整体偏移一个常量**（`0x462000`）——
  只差这一个基址，别无它因。
- 门禁现在把两种形状都覆盖了：语料里加了 `hello_2.13.4`（尾部内嵌 ELF），序言率下限 0.80
  （错位时实测 51–58%，正确时 91–100%）任一种都会失败。原先那条"末指令是终止符"的判据
  已经退役——它其实在数 x64 的 `int3` 填充，地址全错的语料上它照样报 95.7%。

## 值恢复：对象池常量

`ldr x0, [PP, #0x17f8]` 是**对象池**读取。dae 拿它去对照自己已经解析出来的池条目，于是
字面量直接出现在伪代码里：

```dart
rax = "Hello" /* pp+0x17f8 */;   // 原来是：rax = mem(PP + 0x17f7);
```

两种架构都做过源码对照：应用产物里 `"Testing Sample"`（来自它的 `lib/main.dart`）出现 3 次；
2.15.0 产物里出现 `hello.dart` 的 `"Hello"` 与 `" fib(20)="`。内联字面量条数：应用 1922、
hello_3.13.0 556、hello_2.15.0 579、hello_2.13.4 448、hello_3.3.4 403。

**字符串字面量绝不会被折叠进算术表达式。** 寄存器持有的是池槽的**地址**，字面量是**那个地址上
存的内容**——把后者替换成前者是范畴错误，而 Dart 会直接拒绝：`mem((" fib(20)=") + rdx*8 + 0x17)`
就是 `String + int`，即 `argument_type_not_assignable`。`hello_2.18.1` 那一条全语料唯一的 analyze
错误正是这么来的。字面量仍会出现在载入它的那一行（那才是它该在的地方），
不含算术的引用（如 `call(x0)`）也照旧替换。

这条路踩了三个坑，每个都是"先出了错结果"才发现的：

- **x64 的池指针带 tag**：`[PP + 0x17f7]` 指的是 `0x17f8` 那个条目（tag=1），所以查找
  同时试 `偏移` 与 `偏移+1`——池条目间距 8 字节，两个候选不可能同时是条目。
- **不是所有字符串都认得出来**：`describe_into` 用 cid（93/94）判断字符串，老版本的 cid
  编号不同，于是被描述成**类名** `String`。改成按 ref 直接取（`sref_str`）就与版本无关了。
- **池里混着二进制垃圾**（Unicode 数据表那类）。只有"可打印 ASCII、≤60 字符"才内联，
  且自己做转义（引号/反斜杠/换行）；其余保留内存写法加类型注释。这样也守住了
  "产物零非 ASCII" 的仓库口径。

非字符串条目只给类型注释（`mem(PP, 0x2d8) /* Field */`），不给值——它们不是 Dart 表达式，
硬造一个比什么都不说更糟。

## 字段名：剩下什么，以及两条可证的恢复路径

AOT 把字段名几乎全删了。`Precompiler::DropFields` 只在非 PRODUCT 构建保留字段名，所以发布产物里
只剩**寥寥几十条**：3.13 arm64 样本里 60 条，真实 Flutter 应用里 366 条——而类有几百个、字段有几千个。
其余的名字是真的没了，dae 不去猜。

剩下两条**互相独立**的可证路径：

1. **Field 簇本身**。存活的 `Field` 对象带 `name_`、`owner_` 和 `host_offset_or_field_id_`。最后一个是
   **Smi**，而序列化时 Smis 被并进 *Mint* 簇（`app_snapshot.cc`："Smis are merged into the Mint
   cluster"），所以它的值能从 Mint 的整数里取回来。那个整数就是字段的**字索引**（字 0 = tags；首字段是
   字 1，泛型类里是字 2——字 1 被类型参数占着），于是 `字节偏移 = 字索引 × word_size`。
2. **访问器名**。隐式 getter/setter（`kind` 6/7）的名字就是字段名——私有字段叫 `get:_items`，公开字段
   就叫字段名本身。它们的函数体只碰一个字段，于是"函数体里恰好一处字段形访问"是**可证**条件：偏移来自
   机器码位移、名字来自符号。两处以上访问、或有读不懂形状的访问，这个函数就整条放弃，不猜。
   （`Color.a`、`Paint._data`、`_HitTestResponse.hasPlatformView` 都是这条路来的。）

两条路在中间对上了：3.13 arm64 样本上，访问器路径独立复现了 **41 条中的 40 条** Field 记录，名字与偏移
**全都一致**；同一 SDK 的 x64 产物上 39/39；全语料 **0 冲突**。这是没有源码时能拿到的最强证据——
一侧读的是快照自己的字段表，另一侧读的是机器码加一个函数符号。

偏移换算在接任何一条路之前就先钉死了，用了四个互不相干的角度：

| 核对项 | 证据 |
|---|---|
| `disp + 1 == 字索引 × word_size` | `_FutureListener.get_result` 读 `[x1, #0x17]`（24 = 字 3）；`get_state` `[x2, #0x1f]`（字 4）；`get_callback` `[x1, #0x27]`（字 5）——四个字段四条全中 |
| 字索引 = 声明顺序 | `_Uri.path` 是非泛型类的第 5 个声明字段 → mint 5 → `0x28`；x64 产物里 `_Uri._initializeText` 读 `[rax + 0x27]` 取 `path` |
| 泛型类整体错开一个字 | `_FutureListener`/`_Future` 是泛型：声明在最前的 `_nextListener` 落在字 2；该类的 `fbm`（unboxed 位图）是 `0x10` = bit 4 = `state`，而 `state` 正是第三个声明的字段 |
| tagged 折算 | `Error.get:_stackTrace` 读 `[r1, #7]`、`Error._stackTrace_assign` 写 `[r1, #7]`——字 1 减去 1 位堆对象 tag |

**产物里长什么样。** 恢复出的名字挂在内存访问后面的**归属注释**里，绝不改写访问本身：

```dart
x0 = mem((local_0), 0x17); /* _FutureListener.result (off 0x18) */  // 0x483fb4
```

措辞是刻意选的：注释断言的是「**owner 类**在这个偏移上的字段是它」，对基址不作任何声称——
dae 不跟踪基址的类型，在不知道基址就是接收者的情况下写成 `this.result` 就是编造。aotopsy 敢写
`base.field`，是因为它做全程序类型推断（`typetrack`）；那条路是把差距补完的正解，列在优化清单里。

实测覆盖（改完门禁全绿、`dart analyze` 错误 0）：

| 语料 | Field 记录 | 访问器新增 | 两源一致 | 冲突 | 被注解的访问 |
|---|---|---|---|---|---|
| `sample_arm64`（arm64，3.13） | 60 | 1 | 40 | 0 | 218 |
| `hello_3.13.0.aot`（x64，3.13） | 60 | 0 | 39 | 0 | 152 |
| `T4_blank/libapp.so`（x64，2.12.4） | 34 | 0 | 5 | 0 | 43 |
| Flutter `testing_app`（arm64，3.13） | 366 | 1 | 83 | 0 | 438 |

该沉默的地方就是沉默：字段被删、访问器又被树摇掉的应用类（例如 Flutter 样本里的
`Favorites._items`）拿不到名字，因为快照和符号里都没有。`dae fields <binary>` 只列真恢复出来的东西，
并标出每行的来源（`rec` / `accessor`）；导出产物里同一张表落在 `text/fields.txt`。

`tests/field_names.rs` 把这一切盯住：每条语料的记录/一致数下限、**零冲突**、探针字段必须落在确切偏移上，
以及最能抓编造的一条——产物里出现的每个 `/* 类.字段 (off 0x..) */` 都必须在恢复表里有同名同偏移的条目，
且偏移按 `word_size` 对齐。

## 又两个坑，都是加语料加出来的

新增一条 **arm64 ELF** 语料（`testing/variants/h212keep_linux_arm64.exe`——门禁语料里唯一缺的
平台/容器组合）之后，结构化率从 ~88% 掉到 **34%**，并冒出 55 条 `dart analyze` 错误。三个独立原因：

1. **没有落空后继**：条件分支落在函数**最后一个块**时，它后面没有后继——因为表给的函数尺寸就在
   分支处结束了。结构化器把"落空后继未知"当成了"目标越界"直接放弃，在这条语料上白白损失 713 个
   分支。现在把目标支结构成 `if (…) { … }` 并收尾：**34% → 89%**。
2. **嵌套无上限**：`seq` 每遇一个菱形就往下递归一层，1608 个块的函数能钻到约 50 层——产物变成
   阶梯状的 `}`，Dart 解析器直接报 `stack_overflow`（嵌套过深）。现在封顶 10 层，更深的区域
   平铺发射并如实写 `gotoLabel` + 函数头 `NOTE`。
3. **是门禁的 bug，不是产物的 bug**：池里内联出的字符串字面量本身是 `}`（`BARRIER = "}" /* pp+0x2410 */`），
   把形态门禁的花括号计数带偏了。语句结束判据早就屏蔽了字面量，花括号计数没有——改正门禁一侧。

同一文件上再对一次 aotopsy：两个工具都能读的语料上 dae 结构化 89%、aotopsy 63%，
`dart analyze` 错误 0 vs 约 7 万，见 [`COMPARISON.zh.md`](COMPARISON.zh.md)。

## 已知短板（优化清单）

1. 共享尾块与不可归约循环：**前向**跳进已发射块的用尾复制处理（`dup_tail` 把那段直线代码再写一遍，
   打 `duplicated tail` 注释；限 16 块 / 每函数 256 条语句），真实应用里救回 66 个函数。
   **回头**跳到非循环头块的属于真正的不可归约循环（实测 715 处，`is_loop_header=false`）——
   Dart 没有 goto 就表达不了，保留 `gotoLabel` 与函数头 `NOTE` 标记。
2. `unmapped` 现在多数语料只剩个位数（真实应用 3 行、3.3.4/3.4.0 各 1 行），靠最后一轮 lift
   （`xchg`/`idiv`/`sbc`/`adc`/`umulh`/`clz`/`stxr`/`br`/`msub`/`fcvtm*`、SSE 搬移与转换），
   机器专有的操作写成声明的占位函数调用（`Op::Helper`）而不再落到 `// unmapped:`。
   `csel` 的条件现在会跟着上一条 `cmp` 折出真条件（`(x0 == x1) ? a : b`，不再是 `(hi) ? a : b`）。
3. **老旧 x64 可执行文件（2.12–2.14、3.3.4）从来就不弱**——64–69% 是读错字节说出来的数字。
   地址修好后它们稳在 **87–91% 结构化、21–231 行未映射**，与其它版本同一档。真正剩下的问题：
   **内存目的地的** `add`/`or`/`sub`/`inc`/`dec`（`add byte ptr [rax], 8`），以及表给的 code size
   把函数截在最后一个分支目标之前造成的 `.byte` 段。
4. 类型恢复只做了一半：池**值**已解析、字段名也归了属（都在上面），但**基址的类型**没跟踪，
   所以访问写成 `mem(base, disp) /* 类.字段 (off 0x..) */` 而不是 `base.field`。补这一步和
   aotopsy 的 `typetrack` 是同一件事：从调用点、池条目和接收者槽做全程序传播。
   局部变量与参数仍是 `dynamic`。
5. **调用点不显示实参**，于是调用方准备的寄存器看起来像死写：`x1 = NULL; x2 = 6; sub_0x2bb1d0();`
   ——这是 `unused_local_variable` 警告的主要来源（整个 Flutter 构建 10,023 条，160 行的真值语料
   1,475 条）。写成 `sub_0x2bb1d0(x0, x1, x2)` 看着 trivial，但**现在还不诚实**：某个实参寄存器可能是在
   一次**中间调用之前**写的（Dart 的栈溢出 stub 会保留接收者，所以下一个 `bl` 处 x0 仍有效），而 dae
   手里没有经过验证的**各 ABI 破坏寄存器表**——有了它就能算真正的活跃性，再把实参写出来。
   已经试过并撤回，正是被真值语料抓出来的（x0 是 8 条指令、一次调用之前写的）。
6. 前导声明是每文件机械生成的；更聪明的做法是只声明用到的，并给占位函数真实签名。
