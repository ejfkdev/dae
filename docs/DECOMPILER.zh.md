# 反编译质量基线

`--decompile` 的产物是**伪代码，同时也是合法 Dart**：能解析，能过 `dart analyze` 且零错误。
这就是验收线——它是唯一不依赖我们自己"看着还行"的判据：真正的前端得点头。

英文版：[`DECOMPILER.md`](DECOMPILER.md)。

## 判据怎么跑

两条检查，签出即可复现：

```bash
cargo test --release --test dart_valid              # 门禁：每个可用语料都要求 0 错误
cargo test --release --test dart_valid -- --ignored --nocapture   # 全量基线（25 个 SDK 产物）
cargo test --release --test decompiler_shape       # 形态门禁 + 地址自洽性门禁
cargo test --release --test field_names            # 字段名恢复：两源一致 + 零冲突
cargo test --release --test source_truth           # 现编 tests/fixtures/truth.dart，反编译后对源码判
DAE_TRUTH_ANDROID=1 cargo test --release --test source_truth   # 同一套判据跑压缩指针 arm64 产物
DAE_REQUIRE_GATES=1 cargo test --release           # 把所有「缺依赖，跳过」变成失败
```

最后这条比看上去要紧。6 个门禁文件里有 5 个要吃被 gitignore 的语料（`testing/`、
`dart/dart_samples/`），缺了就自行跳过，而 `cargo test` 默认把提示吞掉——于是新克隆会报告
「套件全绿」而实际几乎什么都没量。`DAE_REQUIRE_GATES=1` 让这类跳过直接失败，
这是区分「门禁通过了」与「门禁根本没跑」的唯一办法。

`tests/source_truth.rs` 是唯一**输入是源码**的门禁：用本机 `dart` 编 `tests/fixtures/truth.dart`，
反编译后断言源码说必须留下来的东西——快照里归属该库的每个函数都渲染出来、`main` 会走到的字符串常量
被内联、`Account.withdraw` 保留 `-1` 分支与比较（未被内联时）、产物零 `dart analyze` 错误、解析不漂移。
安卓变体对 `flutter assemble` 现编的 arm64 **压缩指针**产物跑同一套判据（刻意绕开 Gradle：
它首跑会长时间卡在依赖下载上）。

**门禁要能自证。** 一个「什么都没量到也能通过」的门禁比没有门禁更坏——这个仓库为此付过两次学费
（序言率检查替掉了「末指令是终止符」检查，后者在地址全错时照样 95.7%，因为它在数 x64 的 `int3` 填充）。
所以两个 `dart analyze` 门禁都会拿**工具自己的退出码与总结行**（`No issues found!` / `N issues found.`）
反查自己的解析结果：rc=0/1/2 必须解析出 0 个 error、rc=3 必须解析出至少 1 个，且总结行必须出现。
`dart analyze` 指向不存在的目录时返回 rc=64 + usage 文本，里面一条 `error - ` 都没有，
旧解析器把它读成「0 错误」——对一份根本没被分析过的产物盖了通过章。现在每个门禁都带一条
`*_rejects_directory_it_never_analyzed` 自检测试，那个洞一回来就失败；`dart_valid` 还额外断言
每个语料都真的产出了文件与函数，于是「产物为空」再也不能冒充「产物干净」。

`tests/dart_valid.rs` 对产物目录调 `dart analyze`，只数 `error -` 行：警告与提示（未使用变量、
未使用 import）不计——它们不影响"能不能编译"。`dart` 不在 `PATH` 时整条测试自动跳过，
所以在没有 Dart SDK 的机器上不会变成红。

为了"合法 Dart"，一共要处理这些（都在 `src/decompiler.rs`）：

- **机器语法不是 Dart**：`[x2, #0x3f]`、`#0x30`、`qword ptr`、`v2.2d`、`goto L40a8;`、
  `call foo`、`a, b = mem(...)` 全是解析错误。内存改成 `mem(base, disp)` / `memSet(base, disp, value)`，
  间接调用 `callIndirect(x8)`，无法结构化的跳转 `gotoLabel(0x..)`，SIMD 车道 `v2_2d`。
- **名字必须是标识符**：mixin application 的类名带 `&`（`Set&_LinkedHashBase&…`），而 `&` 在 Dart 里
  是运算符；保留字（`rethrow`）与伪运行时占位名（`toDouble`）要改名；同一文件里算出同名的
  两个入口加 `_2`/`_3`。
- **每个文件一段"伪运行时"前导**：声明机器层概念（`mem`/`memSet`/`memRead2`/`callIndirect`/
  `gotoLabel`/`addr`/`abort`/…）以及正文用到但本文件没定义的名字（寄存器、跨库调用目标）。
  这不是"假装编译得过"——它把「机器层到哪里为止、Dart 语义从哪里开始」显式写了出来。

修的过程（按 `dart analyze` 报出来的顺序；数字取自真实 Flutter 应用：412 个文件、
10 245 个函数）：

| 阶段 | `error -` 条数 | 主因 |
|---|---|---|
| 首次测量 | 680,515 | 表达式里带 `[..]`/`#`/`goto`/`call` |
| 内存/调用/跳转改写 | 40,347 | 寄存器与函数未声明 |
| 前导声明 + 文件内改名 | 7,950 | `mem(mem(..))` 套娃、`v2.2d` 声明 |
| 寻址修饰 + x86 尺寸前缀 | 1,800 | `qword ptr` 里含 `word ptr`、`ds:` |
| 条件与 `Node::Line` 兜底清洗 | 4 | `if (…)` 里的 `qword ptr [..]` |
| 保留字 / `print` / 成对写栈槽 | **0** | — |

## 性能

`DART_AOT_PROF=1` 会打印 `render` 的分阶段耗时。加它是因为 release 开了 LTO，调用树被内联打散，
`sample` 把约 86% 归给 `start`、dae 自身符号最高才 0.6%——照着那个猜，先后做出两处
「输出一致但无可测收益」的改动，最后是靠计时才找到真因。

`material_3_demo`（15 082 个函数、985 900 条语句）与真机产物：

| 产物 | 之前 | 之后 | 产物 |
|---|---|---|---|
| `material_3_demo` | 113.5 s、峰值 236 MB | **3.4 s、217 MB** | 逐字节一致 |
| 飞书 3.6.1（安卓） | 181.3 s | **1.6 s** | 指标一致、analyze 0 错误 |
| Reqable.app 3.3.4（macOS） | 156.0 s | **1.0 s** | 指标一致、analyze 0 错误 |
| 微博 2.19.6（安卓） | ~214 s | **5.6 s** | 指标一致 |

病因是两处**每函数重建一次的全局不变数据**：`lift` 自己调 `roles(analyzer)`，而 `roles` 会构建
整张对象池映射（`BTreeMap<u64, String>`，Reqable.app 有 122 064 条）；`Structurer` 又按值持有
`Roles`，于是 `emit_function` 每个函数都深拷贝一遍同一张表。两处都改成借用。修复后各阶段：
lift 1.91 s（66.8%）、emit 0.71 s（25.0%）、前导 0.14 s、CFG 0.03 s。

这也推翻了本文档早先「`--decompile` 的时间主要花在约 100 万次 `format!`」的说法：渲染只占
render 的 5.7%；剖析里那些分配密集的叶子是**池表被反复重建**，不是语句格式化。

### 第二轮：寄存器别名表

lift 仍占 66.8%，下一个逐指令开销是 `mask_regs`——它改写 capstone 的操作数文本
（`x15` → `SP`、`x27` → `PP`）。它**每次调用都重建别名表**：克隆 profile 的 `register_aliases`、
追加 `pp`/`thr` 与九个硬编码项、按 key 长度降序做稳定排序，然后每个 pair 各跑一次
`replace_word`——而每次 `replace_word` 都分配一个新 `String` 并把整段文本重扫一遍。约 100 万条
指令 × 20 个 pair = 两千万次分配与两千万次全文扫描。这张表对整个 run 是不变量，所以现在只在
`roles` 里建一次，`mask_regs` 变成单遍：按 `replace_word` 用的同一个 `[A-Za-z0-9_]` 词边界切
token、查表、分隔符整段拷贝。

单遍查表**并不**天然等价于顺序替换，因为替换会级联。arm64 profile 把 `x29` → `fp`、`x30` → `lr`
（小写），硬编码表尾再 `fp` → `FP`、`lr` → `LR`；按长度降序稳定排序后三字符键先跑，所以 `x29`
最终是以 `FP` 而不是 `fp` 进入产物。因此 `build_mask_map` 是**按原有 pair 顺序模拟整条链**来解析
每个键，而不是做图可达性——可达性会把「值等于某个**更早**的键」也算进去，而顺序替换从不回头再
应用它。`xzr` → `xzr` 这类自映射也自然落对。

| 产物 | 第一轮 | 第二轮 | 产物 |
|---|---|---|---|
| `material_3_demo` | 3.4 s、217 MB | **2.1 s、188 MB** | 逐字节一致 |
| ↳ `lift` 阶段 | 1.95 s（66.7%） | **0.63 s（40.3%）** | 3.1× |
| ↳ `emit_function` | 0.73 s | 0.71 s | 不变（不在这条路径上） |
| 飞书 8.0.2（安卓 arm64） | 1.56 s、174 MB | **1.41 s、167 MB** | 逐字节一致 |

计时是三轮交错 A/B（3.51/3.67/3.45 → 2.08/2.29/2.13 s）；同一二进制在主机有无关负载时会飘约
35%，所以单次跑数不算证据。字节一致用 `diff -rq` 对整棵产物树验过：`material_3_demo`、飞书，
以及五个语料变体（覆盖 Mach-O x64、ELF x64、ELF arm64 与 SDK 2.10/2.14）——**只测 arm64 语料
不会走到 x64 的别名表**。每一项的指标都逐项相同（181 504 块 / 985 900 语句 / 13 950 结构化 /
1 132 未结构化 / 3 行 unmapped）。

已发布 v0.1.8 二进制上的**当前绝对值**（给想知道「现在到底多快」而不是分轮增量的读者；
主机负载 13–20，来自无关进程，所以这些数字当上界看）：飞书 3.6.1 安卓、25.6 MB、25 183 个表项函数
——`--decompile` **1.63 s**；微博 2.19.6 安卓、9 MB、19 053 个反编译函数 / 153 万条语句——**3.51 s**；
`material_3_demo` macOS、14 MB、15 796 个函数——**2.37 s**；不带 `--decompile` 的纯导出，
9 MB 样本 0.26 s、飞书 0.96 s。上面第一轮表里微博仍写 5.6 s，那是它**第一轮**的测量值，
第二三轮把它带到了 3.5 s。

本轮还包含：八处 capstone 引擎构造从 `.detail(true)` 改成 `.detail(false)`。grep 确认全仓没有
任何 detail API 被用到（只用 `mnemonic`、`op_str`、`address`、`bytes`），所以这是**严格更少的
工作量**，但 A/B **测不出加速**（差异落在主机噪声内）。保留它的理由是「不会更差」，上面那些
数字里不含它的贡献。

### 第三轮：内存，以及它到底在哪

峰值 RSS 是**量出来**的，不是猜的；路上死了两个假设：

- `dae info`（只解析）峰值 **41 MB**，完整导出 **151 MB**。所以内存问题**不在反编译器**——
  解析很便宜，是导出管线持有约 110 MB。
- 用 `--no-default-features` 构建（去掉 `asm` + `callgraph`）峰值 **60 MB**，
  这两个导出器占了峰值里约 91 MB。
- 最像嫌疑犯的那个是错的：`asm` 每文件一个 `String::with_capacity(job.est)`、最多 8 线程在飞，
  但最大单文件只有 1.3 MB，并发缓冲上限约 10 MB——不是大头。

八个导出器实际是**并发**跑的（`std::thread::scope`，各一线程），所以峰值是它们工作集之和，
这也解释了导出期间 RSS 为何单调爬升、从不回落。

`callgraph` 里有一个真缺陷：边是用
`sort_by_key(|a| (a.from, a.to, a.to_text.clone()))` 排的。**`sort_by_key` 不缓存键**——每次比较
都重调一次闭包——于是每次比较都分配一个 `String`：96 904 条边 × O(log N) ≈ **160 万次克隆**，
更大的应用按比例更多。现在改成借用键排序（`to_text.as_str()`），序完全相同（`String` 与 `str`
都是逐字节字典序）、同样是稳定排序。合并各线程分片时也一次性预留总长，不再让一个约 14 MB 的
`Vec` 反复翻倍。

| 模式 | HEAD | 第二+三轮后 | 产物 |
|---|---|---|---|
| 仅导出 | 169/164/175 MB、约 0.48 s | **138/140/149 MB、约 0.48 s** | 逐字节一致（506 文件） |
| `--decompile` | 220/223/212 MB、3.89/4.22/3.52 s | **180/180/173 MB、2.55/2.08/2.31 s** | 逐字节一致 |

各三轮交错，主机负载约 7.5——绝对值偏高，但配对是公平的。注意这里**没有**声称的事：
callgraph 那一改买到的是内存与消除 160 万次分配，导出墙钟并没有可测变化（排 9.6 万条边本来就快）。

字节一致用 `diff -rq` 对整棵树复验过：`material_3_demo` **两种模式**、飞书、以及五个语料变体；
`call_edges.txt` 逐行相同（96 904 / 12 011 行），这正是新比较器排序一致的直接证据。
记一个假警报：有一次 `diff -rq z_old z_new` 用了相对路径、而 cwd 不对，报出的「差异」其实只是
diff 找不到目录的退出码 2。可靠做法是用绝对路径，并确认 `diff` **没有输出**。

### 第四轮：产物改流式，再把反编译器并行（2026-09-28）

前三轮把反编译器本身弄快了。这一轮动的是仍然拖着**整次导出**的两件事：产物在内存里攒着、
以及反编译器在 18 核机器上是单线程的。

**内存到底在哪**（实测，不是猜——用 `DAE_SKIP_ASM` / `DAE_SKIP_CG` 隔离跑 material_3_demo，
15 082 函数）：

| 关掉什么 | 峰值 RSS | 归因 |
|---|---|---|
| 都不关 | 137.6 MB | — |
| `asm` | 100.0 MB | asm 导出器 ≈ **37.6 MB** |
| `callgraph` | 107.5 MB | callgraph ≈ **30.1 MB** |
| `--no-default-features` 构建 | 60.5 MB | 解析 + 对象层 ≈ 41.9 MB（`dae info`） |

有两个**猜错的**方向值得记下来。(a) 不是 capstone：`dae disasm` 单函数 42.8 MB vs `dae info`
41.9 MB，一个实例 ~0.9 MB，8 个才 ~7 MB。(b) 也不是产物体积：最大的 10 个 `asm/` 文件加起来
只有 8.6 MB。大头是**分配高水位**——`asm::write` 把每个库攒进 `String::with_capacity(est)`，
而 `est = 96 + mangled.len() + csize*12` 对 arm64 **低估约 2 倍**（每 4 字节指令要渲染成一条
机器码注释 + 一条 IL 注释，约 90–100 字符），于是每个缓冲都要翻倍扩容，8 个线程循环处理 489 个
任务，freed 的页又不还给 OS。

**改法 1——产物流式化。** `asm::write` 改成固定 256 KB 的 `BufWriter`（每线程占用与文件大小
**无关**），不再攒整份。反编译器更严重：`render` 返回 `Vec<(String, String)>`，把
**505 份文件共 63.2 MB 一次性全拿着**，而 `full = preamble + of` 还会把最大的那份（4.2 MB）
再拷一遍。现在 `render_into` 收一个 sink，`write()` 每个库渲染完就直接落盘，stdout 子命令
仍然收集。实测：带 `--decompile` 183.2–186.9 → 141.3–157.6 MB（-18%），不带
140.0–144.1 → 128.0–131.2 MB（-9%）。

> ⚠️ `write()` 仍然必须**无条件** `create_dir_all(dart/)`，即使一份文件都不产。
> `hello_2.10.4.exe` / `hello_2.7.2.exe` 只有对象层、没有指令表，按设计不产伪代码，
> 而 `dart_valid::full_scorecard` 会对每个样本的 `dart/` 跑 `dart analyze`——
> 「0 文件 0 错误」是合法结果，「目录不存在」才是失败。把建目录挪进 sink 之后 scorecard 立刻红。

**改法 2——按库并行。** `render` 原来是 505 个库的单线程循环，占 3.0 s 墙钟里的 2.49 s。
各库之间只受两条「首见生效」规则约束，所以现在先用一趟廉价的顺序预扫描把它们定死，再开始渲染：

* **文件名**——大小写不敏感去重，第二个撞名的加 `_2` 后缀；
* **每个入口地址归哪个库发射**——代码共享时一个机器码地址可能被多个 `Function` 对象引用，
  旧代码只让**第一个认领它的库**发射（全局 `seen: BTreeSet`）。预扫描把它固定成
  `owner: ep → 库序号`。

`owner` 要做对还差一块：那一个全局 `seen` 其实在干**两件事**。只换成 `owner` 会让同一个库在
两条 `FuncEntry` 共享一个 `ep` 时（一批同体 getter）把该地址发射两次，表现为
**15 082 → 15 367 个函数**——多出 285 个重复。补一个每任务独有的 `seen_local` 才恢复原语义。

并发度就是满的 `n_threads()`（本机 = 8），与其它导出器同一个口径。每线程的工作集**确实**是
「一整份库正文」——前导声明必须等正文渲染完才算得出来，没法流式掉，而库的大小极不均匀
（最大 4.2 MB）——所以这条曲线是**测出来的**，不是假定的（每档 3 轮）：

| 并发 | 墙钟 (s) | 峰值 RSS (MB, 均值) |
|---|---|---|
| 串行（改前） | 2.98–3.03 | 184.3 |
| 1 | 3.09 | 159.7（流式化单独的收益） |
| 2 | 1.83–1.90 | 175.0 |
| 3 | 1.43–1.51 | 178.7 |
| 4 | 1.23–1.25 | 205.0 |
| **8** | **0.96** | **206–235** |
| 12 | 1.12–1.24 | 235–241 |
| 18 | 1.08–1.15 | 267 |

墙钟很稳，RSS 有 ±25 MB 噪声。**8 是甜点，再往上两项都变差**：本机 18 个逻辑核里只有 6 个
性能核，超过之后任务落到能效核上，而共享队列里一个慢线程拿着大库就拖住收尾（12/18 线程反而比
8 慢 0.1–0.3 s）。所以本项目的「默认拉满」就是 `n_threads()`，不是核数原值。
`DAE_DEC_THREADS` 可覆盖，方便不改代码重编就重测曲线。

正文缓冲的容量预估也一并修准了。原来是 `n_fns * 768`，而 material_3_demo 实测膨胀是
**≈16.6 字节 Dart / 字节机器码**（3.8 MB 代码 → 63.2 MB 产物；`asm/` 是 46.3/3.8 ≈ 12.2，
正好等于 `asm.rs` 里已有的系数，互为交叉验证），所以旧预估**低估 5.4 倍**、每个缓冲都要翻倍
好几次。现在预扫描按库累加 `csize * 18`。8 线程下交替 A/B：墙钟 1.08–1.16 → 1.04–1.12 s、
RSS 均值 221 → 210 MB——幅度不大，但三对里**方向一致**。

**净效果，交替 A/B（4 轮，material_3_demo）**：带 `--decompile` 3.04–3.05 s / 181–200 MB →
**1.42–1.43 s / 178–184 MB（快 2.13×，内存持平略降）**；不带 0.56–0.58 s / 139–142 MB →
**0.55 s / 124–130 MB（-9%）**。产物**逐字节一致**：material_3_demo（1011 个文件）与另外六个
语料（arm64 Mach-O、x64 Mach-O、x64 ELF、两个真机 Android `libapp.so`、压力样例）`diff -rq`
全干净。门禁全绿：59 个测试、`full_scorecard`（26 样本 / 291 文件 / 24 253 函数 /
`dart analyze` 0 错误）、`regress_all` 25/25、`check_profiles` 47/47、clippy 0。

## 三个 2026-09-28 用「源码对照」找到的缺陷（都已修）

拿有源码的 example 逐个函数对照，比任何形态指标都有效——这三个缺陷**对既有门禁全部隐形**。

1. **待定值被静默丢弃**（`nest_block`）。遇到 `Op::Note`/`Op::Cmp` 等语句时原先是
   `pending.clear()`，而 `push`/`pop` 正是调用实参准备链的终点：x64 上
   `mov rcx,rax; sub rcx,1; push rcx; call fib` 折成的 `rcx = rax - 1` 被扔掉，
   产物里 `fib()` 既没有实参、也没有任何一行提到 `n - 1`，而且**不计入 unmapped**
   （指令是认得的，只是结果被扔了）。改成与 `Call`/`Store`/`Branch`/`Return` 一致的
   **落地**。实测 material_3_demo 的 dart/ 从 1,998,350 行增到 2,165,737 行（+8.4%），
   `DecompileStats` 一字未变（统计发生在 `nest_block` 之前）——所以摘要指标看不见它。
   门禁：`decompiled_body_covers_instruction_addresses`，判据是「asm/ 里的真指令地址有多少
   能在 dart/ 的语句地址注释里找到」，修复前 70.1%、修复后 78.3%、门槛 75%（已负测）。
   取舍：曾试过只对 `Op::Note` 落地（+3.0% 行数），但它仍会丢掉 `rax = mem(FP+0x10)`
   这类在 `Cmp` 处被清的参数载入，所以选了统一落地。
2. **`condFlag` 包住了本来合法的表达式**。`cbz`/`cbnz`/`tbz`/`tbnz` 在 lift 阶段就生成了完整
   Dart 布尔表达式，但分支统一又过一遍 `fold_cond`；`fold_cond` 是按**助记符**匹配的，
   匹配不到就落到兜底 `condFlag("{mnem}")`。判据用「含不含空格」（助记符从不含空格，
   两条自带条件的生成式一定含空格）。实测 14,886 → **2,841** 处，剩下的全是
   `vc`/`vs`/`eq`/`ne`/`hs`/`lo` 这类真需要占位的裸条件码。门禁
   `condflag_only_wraps_bare_condition_codes`（已负测）。
   效果示例（自编压力样例的 `switch` + 三目）：`if (condFlag("w1 & (1 << 0) != 0"))` →
   `if (w1 & (1 << 0) != 0)`，一眼能认出源码的 `n.isEven ? 'even' : 'odd'`。
3. **`dae classes` 把「库的顶层函数」当成一个空名类列出**。空名按字典序**排在最前**，
   于是 `dae classes x | head -1 | cut -f3` 拿到空串（评估脚本真的被打断过），计数也失真
   （本语料 300 行里 12 行空名，而 `text/classes.txt` 是 544 条真 Class 记录）。
   现在跳过它们并在计数行**如实报出**跳过了多少（顶层函数在 `dae functions` / `dae members`
   里照常可见）。同一处还补上了口径说明：本命令只列**有函数**的类，`text/classes.txt`
   列全部 Class 记录，两者能差很多（animations 实测 2177 vs 3358，差的那些方法全被内联/树摇）。

## 第二个压力样例又找出四个缺陷（2026-09-28，修三撤一）

第一轮是拿 `if`/循环/类/集合的源码对照产物。这一轮**另写了一个样例**，覆盖此前所有语料都没碰过的
构造：`async`/`await`、`async*`/`yield`、泛型（`Box<T>`）、extension 方法、运算符重载
（`+`、`==`、`hashCode`）、级联、带成员的 `enum`、`mixin`、`abstract`、`late`、可空类型。
它能编译、能跑、反编译产物也过 `dart analyze` 0 错误——**仍然暴露出四个缺陷**。

1. **arm64 的 `cset`/`csetm` 整条消失**——两个 bug 互相掩盖。
   `lift_one` 直接用**裸条件码**拼三元式：`(ne) ? 1 : 0`。`ne` 不是 Dart 标识符，本该报
   `undefined_identifier`；`csel`/`csinc` 走 `sel_cond()`/`fold_cond()`，而 `cset`/`csetm`
   漏在 `lift()` 那个 `matches!` 列表外面。这段非法文本之所以从没暴露，是第二个 bug 挡的：
   `nest_block` 对 `Expr::Text` **不做待定值替换**（只有 `Expr::Mem` 做），而 pending 按 dst 建键，
   于是紧随的 `x2 = (x2 << 1)` 直接覆盖掉 cset 那条，语句凭空消失。
   **净效果是静默的错误值，不是少一行。** 样例里
   `int get rank => this == Level.low ? 0 : 1` 被 AOT 内联成
   `cmp x1, <Level.low>; cset x2, ne; lsl x2, x2, #1`；修复前产物只剩 `x2 = x2 << 1`，
   而 x2 还是八条指令之前设的 `4`——那是**插值数组的长度**。修复后是
   `x2 = ((x1 != BARRIER) ? 1 : 0) << 1`。
   还需要第三处：`NEST_MAX_DEPTH` 挡住替换时，待定值必须**落地成语句**，不能留在 pending 里等着
   被覆盖。`_BigIntImpl.get_hashCode` 正是这么丢的——深度限制在 `asr r4, r5, #1` 处停下折叠，
   紧接着 `ldur r5, [r2, #0xf]` 覆盖 `pending[r5]`，整条哈希计算（含那个三元式）全没了。
   现在它单独落地成 `x5 = (((x4 == 0x10) ? -1 : 0) & ...) + ...`，比一行 110 字符的嵌套更好读。
   门禁：`cset_instructions_materialize_as_ternaries`——按函数统计，函数体里 `? 1 : 0` /
   `? -1 : 0` 三元式个数 ≥ 该函数 raw 反汇编注释里 `cset`/`csetm` 的条数。已负测：v0.1.9 上是
   **8 条指令 / 0 个三元式 / 8 个函数不合格**，修复后 7 / 9 / 0。
2. **raw 反汇编注释块越过了函数边界。** `lift` 有意多反汇编 16 字节（Code 对象的 size 常把最后
   一条指令截断在中间），`stmts` 一直有 `stmts.retain(|s| s.addr < limit)` 裁剪，**`raw` 漏了**。
   于是每个函数尾部都会印上最多四条**属于下一个函数**的指令（`_Record.get_hashCode`：
   entry `0x49e12c` + size `0x12c` ⇒ 边界 `0x49e258`，注释块却印到 `0x49e264`，多出的
   `csetm x0, eq` 不是本函数的——`dae disasm` 的 IL 到 `0x49e254` 就结束了，可对照）。
   门禁 1 那一条误归属正是它造成的。现已裁剪。这也是 `dart/` **变小**的原因：七个语料 -2.5%~-3.5%。
3. **x86 的 `setcc` 完全没有 lift 分支**，退化成 `// unmapped: setne dl`。这是**诚实**的
   （不像缺陷 1 那样凭空消失，而且计入 unmapped 指标），但那个布尔条件白丢了。`setcc` 是 arm64
   `cset` 的对应物，现在走同一条路径；条件码按前缀映射到跳转助记符（`setne` ↔ `jne`），
   且**只认 `fold_cond` 真能处理的那 26 个后缀**，其余一律不接管（继续 unmapped），
   绝不编一个 `condFlag("j…")` 出来。
   门禁：`x86_setcc_materializes_as_ternary`。已负测：v0.1.9 是 **9 条指令 / 0 个三元式 /
   8 条 unmapped**，修复后 8 / 8 / 0。
4. **已撤回：把立即数字面量折进待定值。** 收窄 `subst_regs` 的「纯寄存器别名」守卫、让单 token 的
   **字面量**也参与替换，看着很划算——`mov r17, #0x1cf2; movk r17, #0xd, lsl #16` 就能从自引用的
   `x17 = (x17 & 0xffff) | 0xd0000` 变成常量可读的 `x17 = ((7410) & 0xffff) | 0xd0000`。
   **但它会打破 `dart analyze`**：伪码里寄存器与占位函数全是 `dynamic`，`dynamic - dynamic`
   的静态类型还是 `dynamic`（什么运算符都能用），而一旦一边换成 `int` 字面量，
   `int - dynamic` 的静态类型就变成 `num`——`num` 没有 `<<`/`&`/`|`。
   `_Smi.get_bitLength` 因此变成 `((64) - (clz(x0))) << 1` 并报 `undefined_operator`，
   T4_blank 同样失败。上面三个修复都**不依赖**它（有了缺陷 1 的落地，三元式照样出现），所以撤掉。
   要拿回这个可读性收益，得先给前导声明一套自洽的类型（让占位函数返回 `int` 而不是 `dynamic`），
   是独立工程。

七个语料（arm64 Mach-O、x64 Mach-O、x64 ELF、三个真机 Android `libapp.so`、一个自编样例）上，
净效果是每一项都同时变好：**非 `dart/` 产物逐字节一致**、**块数与语句数完全不变**、
unmapped 行下降（42→34、166→161、25→22）、`dart/` 体积降 2.5–3.5%、条件三元式从
**每语料 0 个变成 3–10 个**。常设门禁全绿：58 个测试、`full_scorecard`
（26 样本 / 291 文件 / 24 253 函数 / `dart analyze` 0 错误）、`regress_all` 25/25、
`check_profiles` 47/47、clippy 0。

## 第三个压力样例：写 w 寄存器不与读 x 寄存器联动（2026-09-28，已修）

第三个样例覆盖前两轮都没碰的东西：Dart 3 的 records、模式 `switch` 表达式、`sealed` 类、
`sync*` 生成器、函数 typedef、spread / collection-`if` / collection-`for`、`rethrow`、
`static`/`const`，以及**故意写的位运算密集代码**（一个带 rotate 的 FNV 式哈希）。
它能编译、能跑、反编译产物 `dart analyze` 0 错误——而那个哈希函数暴露出一个**静默错误值**缺陷。

arm64 上 `wN`（32 位）与 `xN`（64 位）是**同一个物理寄存器的两个视图**：写 `wN` 会把 `xN` 的
32–63 位清零。产物里它们是 `dynamic w4; dynamic x4;` 两个独立变量，于是「先写 `wN`、之后读 `xN`、
中间没有对 `xN` 的写」读到的是**陈旧值**。`hashBytes` 里源码的 rotate
`((h << 5) | (h >> 27)) & 0xffffffff` 编译成 `w4 = w1 << 5; w6 = w1 >> 27;`，
修复前产物是 `x0 = ((x4 | x6) >> 0) & 0xffffffff`——x4/x6 是几个指令之前的旧值。
修复后是 `x0 = ((((w1 << 5) & 0xffffffff) | ((w1 >> 0x1b) & 0xffffffff)) >> 0) & 0xffffffff`。

修法是每写一次 `wN` 就补一条别名赋值 `xN = wN & 0xffffffff`，`nest_block` 会把它折进后续表达式。
**「把 wN 改名成 xN」这个方案被否决**：`w4 = w1 + w2` 的真值是 `(w1 + w2) mod 2^32`，
直接改名就丢了截断；而只改写入端又会让后续**读** `wN` 的地方变成未定义变量。

material_3_demo 实测：陈旧读 **3 590 → 16** 处（波及函数 1 135 → 13，即 7.6% → 0.1%）；
语句数因别名行 **+1.5%**（985 900 → 1 000 974）。门禁
`w_register_write_aliases_x_register`（门槛 40 处陈旧读，并断言 w 写入 ≥ 20 处以免空过），
**已负测**：换回修复前的二进制报 290 处并失败。

本轮两个测量陷阱，值得留着：

* **`DART_AOT_PROF` 的百分比现在会超过 100%**（lift 271%、emit 357%）。这不是计时错乱——
  各阶段是**跨线程累加的 CPU 时间**，而「主循环」那行是墙钟。想看单线程口径就
  `DAE_DEC_THREADS=1`。打印里已经写明。
* **单次墙钟读数不可用。** material_3_demo 有一次跑出 3.42 s，而干净重测三轮是 1.09–1.22 s——
  那次紧跟在同一条命令里的 `unzip` 之后、且机器已经连续 benchmark 了一小时。
  必须交替 A/B 且跑多轮；峰值 RSS 比墙钟稳定得多。

## 靠枚举 `// unmapped:` 一次补掉六个 lift 缺口（2026-09-28）

这一轮没有再写新样例，而是**把所有语料里未映射的助记符全量枚举**——每一个不同的助记符就是一个
具体的 lift 缺口，所以这份枚举本身就是 bug 清单。改前：material_3_demo 3 条、
hello_3.13.0（x64）161 条、T4_blank（x64）34 条。

| 助记符 | 含义 | 现在渲染成 |
|---|---|---|
| `addsd` `subsd` `mulsd` `divsd`（含 `ss`） | x86 SSE 标量浮点，**两**操作数（`xmm0 = xmm0 op xmm1`） | `(a op b) /* float */`，与 arm64 的 `fadd`/`fmul` 共用一条路径 |
| `comisd` `comiss` `ucomisd` `ucomiss` | 浮点比较，只设标志位 | 归入 `cmp` 家族，于是紧随的 `ja`/`jb` 能折出真条件 |
| `cmov<cc>` | 条件传送（x86 版的 `csel`） | `(cond) ? src : dst`，复用 `sel_cond`/`fold_cond` |
| `cinc` `cinv` `cneg` | arm64 的 `csinc`/`csinv`/`csneg` 别名 | `cond ? xn+1 : xn` / `cond ? ~xn : xn` / `cond ? -xn : xn` |
| `inc` `dec` | ±1 | `dst = dst + 1` / `- 1` |
| `cdq` `cqo` | `idiv` 之前把 eax/rax 的符号铺进 edx/rdx | `edx = ((eax >> 31) & 1) == 0 ? 0 : -1 /* cdq: … */` |

改后：material_3_demo **3 → 2**、hello_3.13.0 **161 → 142**、T4_blank **34 → 9（-74%）**。
26 个样本 / 24 253 个函数的 `dart analyze` 仍 0 错误，60 个测试全绿。

其中 x86 标量浮点是实质性的那条：x64 上**所有** `double`/`float` 算术都走 `*sd`/`*ss`，
漏掉它们等于 x64 快照里的浮点运算全部变成 `// unmapped`。漏的原因是**两操作数形态**——
arm64 那条路径只认三操作数的 `fadd d0, d1, d2`。

**剩下的，以及一个值得点名的陷阱。** 剩余 142 条里有 **121 条是指令前缀**
（`rep` 61、`std` 30、`cld` 30、`lock` 3），capstone 把它们当独立指令报出来；
正确修法是**把前缀与紧随的指令合并**（`rep movsb` 是一个 memcpy 循环），而不是单独映射前缀。
其余是 `mul rdx`（x86 单操作数乘法写 `rdx:rax`，单条赋值表达不了、硬表达就要丢高半部）、
`shld`/`shrd`、`or mem(...), reg`（对内存的读改写）、`bsr`、`subps`/`subpd`。

> ⚠️ 把前缀从 `// unmapped:` 改标成 `// note:` 能让这个数字一次掉 85%，而**信息量为零**。
> `unmapped` 之所以是质量表盘，正因为它数的是「语义没被恢复出来的指令」；不要刷它。

## 一个寄存器名子串匹配捏造出 `ppmem(...)`，吞掉 1411 个 store（2026-09-28，已修）

派子 agent 逐类审计 Reqable（arm64、dart 3.3.4、类名混淆、开了 `dedup_instructions`）时发现的。
线索是一个**纯前缀相关性**：全产物里 16 种不同的 ppmem 位移**全部以 `0x27` 开头**，
而 `mem(..., 0x27*)` **零幸存**，同时 `mem(PP, 0x5270)` / `0x26x` / `0x28x` 全正常。
这个分布是**子串匹配**的指纹，不可能来自任何语义规则。

池加载判定写的是 `ops.contains(&rl.pp)`。Dart arm64 的池指针 PP 物理寄存器是 `x27`，
而位移文本 `#0x27` 里**正好含有子串 `x27`**。于是 `stur x17, [x3, #0x27]` 被判成池加载、
返回 `Expr::Pool(0x27)`，三重后果：

1. **store 变成赋值**——方向反转，`memSet(x3, 0x27, x17)` 这个写**彻底消失**，
   而 x17 被留下持有一个未定义标识符；
2. `Expr::Pool` 渲染成 `pp[0x27]`，再经发射出口的 `sanitize_mem_refs` 把 `[..]` 改写成
   `mem(..)`，于是凭空捏出 **`ppmem(0x27)`** 这个标识符；
3. load 侧丢基址：`ldur x1,[x0,#0x27]` 与二级解引用 `ldur x2,[x1,#0x27]` 渲染成
   **同一个** `ppmem(0x27)`，两层不同的间接被别名成同一个值。

修法：改成**词边界匹配**（`contains_word`，与既有 `replace_word` 同一套边界定义）。
Reqable 实测：`ppmem(` **1411 → 0**、`mem(..., 0x27*)` **恢复 744 处**、被吞掉的
`memSet(..., 0x27..., ...)` 全部回来。agent 报的原始案例 `Agb.uzd` 从 `x17 = ppmem(0x27);` 变成

```dart
x17 = "autoCapture" /* pp+0x2a608 */; // 0xecd0f0
memSet(x3, 0x27, x17);                // 0xecd0f4
```

——所以这一修还**顺带恢复了一个字符串字面量**，它此前被那个假的池索引挡住了。
门禁 `no_register_substring_false_positives_in_output`（断言 `ppmem(` 为 0，并为防空过同时断言
`memSet` ≥ 50 / `mem` ≥ 500；本语料实测 2475 / 9254）。

值得留下的一般规律：**任何 `text.contains(寄存器名)` 形式的判定都是定时炸弹**——
`x27` 是 `0x27` 的子串，`x1` 是 `x17` 的子串。所有寄存器名查找都必须走词边界匹配。

## 可读性优先——试过，并且撤回了（2026-09-28）

出发点是成立的：产物里的位运算测试**通常是编译器优化过的 `if`**，照抄机器形态要求读者本来就知道
对象布局。但第一次尝试据此动手是**错的**，所以记在这里而不是删掉。

**做了什么。** `tbz xN, #0` / `tbnz xN, #0` → `isSmi(xN)` / `isHeapObject(xN)`，依据是 profile 里的
`tagging.heap_object_tag` = 1 与 `smi_mask` = 1——也就是说第 0 位**确实是** Smi/HeapObject 标记位，
而且是从 profile 读的、没有硬编码。在 Reqable 上它产出 1 169 处 `if (isSmi(...))` + 58 处
`if (isHeapObject(...))`，把 `& (1 << 0)` 形态从 1 232 降到 0，`dart analyze` 仍 0 错误，
在 w32-compressed 的安卓语料上同样生效。**每一项指标都说它成功了。**

**为什么是错的。** 位号相同**不代表语义相同**。`tbz/tbnz xN, #0` 也是**未装箱整数奇偶测试**的
编译形态：源码 `return n.isEven ? 'even' : 'odd';`（`testing/stress/stress.dart:31`）编译成
`tbnz w1, #0`，而 w1 里是个 `int`，根本不是 tagged 指针。还原之后产物是

```dart
if (isHeapObject(w1)) { x0 = "odd"; } else { x0 = "even"; }   // ← 编造的语义
```

它告诉读者「如果这是个堆对象」，而真相是「如果这个整数是奇数」。改前的
`if (w1 & (1 << 0) != 0)` 朴素但**正确**。所以这次改动是拿一个正确的表达式换了一个漂亮而错误的——
正是本项目禁止的编造，而且**对所有门禁隐形**：产物仍是合法 Dart、计数仍朝好的方向动，
只有拿源码对照着读才能发现。

要让这个还原站得住，必须先证明「**这个寄存器此刻持有的是 tagged 值**」，那需要类型或数据流信息，
而反编译器没有（产物里全是 `dynamic`）。在那之前位测试保持原样：它是机器真正做的事，
读者可以自己判断这是标记测试还是奇偶测试。

**这次尝试里有两样东西留下了**，因为它们与该功能无关：

* `lift()` 里「这个条件已经是表达式、还是待折叠的助记符」的判定原来是 `c.contains(' ')`。
  这个代理判据被本次改动打破（`isSmi(x0)` 不含空格 ⇒ 被当成助记符 ⇒ 在 `fold_cond` 的表里
  匹配不到 ⇒ 落进兜底 `condFlag("isSmi(x0)")`，判断**躲进了字符串字面量**，比不还原更糟，
  而计数看着还是对的）。现在改成看形状：助记符一定全是小写字母加点（`b.eq`、`jle`），
  凡含大写字母、括号或运算符的都已经是表达式。**不管这个功能做不做，这条都严格更稳。**
* 门禁 `condflag_only_wraps_bare_condition_codes` **本该抓住上面那件事却没抓住**——
  它的判据是「含空格或比较/逻辑/位运算符」，而 `isSmi(w0)` 一个都不含。现在改成要求
  `condFlag` 的参数必须是 1–3 个纯小写字母的裸条件码。
  **教训：门禁判据要按「形状」写，不要按「我目前见过的那几种坏样子」枚举**——
  否则每出一个新 bug 就得补一条特例，门禁永远落后一步。

另一条也留下：新的占位函数必须在 `PSEUDO_FUNCS` 里**显式声明**，不靠前导的自动 `dynamic X;`。
那条自动路径正是捏造标识符 `ppmem` 能长期过 `dart analyze` 的原因——未知名字被声明成
`dynamic` 变量，而调用一个 `dynamic` 是合法的。

**关于剩下的常量。** 审计本轮加进**代码**（不含注释）的每一个数字字面量，只有一处来自对单个 app
的测量：反编译器正文缓冲的预估 `est += csize * 18 + 96`。那个 18 是在 material_3_demo 上量出的
「每字节机器码产出多少字节 Dart」（63.2 MB / 3.8 MB ≈ 16.6，向上取整）；`asm.rs` 对同类预估
独立地用 12，而它自己的比值量出来是 46.3/3.8 ≈ 12.2，互为交叉验证。它**只是容量提示**——
估多估少只影响 `String` 扩容次数，不影响产物的任何一个字节，所以不可能导致结果错误，
但它确实不是从任何普适事实推出来的，产物格式若变就要重新量。
其余常量都是体系结构级的（32 位寄存器视图的 `0xffffffff`、`cdq`/`cqo` 符号扩展的 `31`/`63`）、
ISA 级的（26 项 x86 条件码白名单，与 `fold_cond` 自己的表绑定），或纯粹的 I/O 缓冲大小。

## 少了一行字段——而那正是修复生效的证据（2026-09-28）

发版前与 v0.1.9 对账，`dart/` 之外只有一处字节不同：`text/fields.txt` 从 **634 行变成 633 行**，
少了 `_SyncStarIterator  _current  accessor  0x8`。两个二进制都是确定的（各连跑三次 md5 相同），
且只在 arm64 语料出现，所以追到了底而不是放过去。

访问器推断路径**会跑完整的 `lift` 流水线**（`accessor_fields` 对每个隐式 getter/setter 调 `lift`，
再从得到的 `Stmt` 里读偏移），所以任何 lift 改动都会动到 `text/fields.txt`。它的健全性护栏是：
只有当访问器**恰好**呈现一个字段偏移、且**没有**无法归类的访问时才推断。

`_SyncStarIterator._current_assign` 里有两处字段访问：

```
0x38163c: ldur r2, [r3, #7]      -> 偏移 0x7（去掉 tag 是 0x8）
0x381658: ldur r4, [r2, #0x27]   -> 第二个偏移——而 0x27 里含子串 "x27"
```

在 v0.1.9 上，第二处被池加载的子串 bug 吞掉了（`ops.contains("x27")` 命中位移文本），
被归成 `Expr::Pool`、算作**不是**字段访问——于是只剩一个偏移，护栏通过、那一行被写出来。
改成词边界匹配之后第二处访问被正确识别，`offs.len() == 2`，护栏**拒绝推断**，而这正是它的职责。
另一条佐证是：这个「setter」开头是两次**加载**而不是 `stur`，根本不是朴素字段 setter 的形状，
所以原来那行本身就站不住。

也就是说，那一行是**一个 bug 抵消了另一个 bug 的盲区**才产出的。**634 → 633 是可信度提升，
不是能力损失。** 值得记下来是因为这个耦合是隐形的：`text/fields.txt` 里看不出它依赖反编译器的
指令 lifter，而 `tests/field_names.rs` 检查的是「两条路径互证」与「产物注解都在表里」，
**不检查行集是否稳定**，所以一次 lift 改动可以静默地移动它。

## 两条待办项复查后**决定不动**（2026-09-28）

两条原先都记成「已取证未修」。仔细看之后，它们都不是命名或渲染层面的小调整，而**硬猜会把一个
自洽的读法换成一个无法证明的读法**——与撤回 `isSmi` 还原时定下的判据是同一条。

**post-index 的栈槽不是命名错了，是需要跟踪 SP。** 这一对

```
str q0, [SP, #-0x10]!   ->  local_m10 = q0      （pre-index：先 SP -= 0x10 再存）
ldr q0, [SP], #0x10     ->  q0 = local_0        （post-index：先在 SP 处取，再 SP += 0x10）
```

看着不一致，机器层面确实访问同一个槽位。但 dae 是按**方括号内的位移**给槽位命名的，而 `[SP]`
没有位移，所以 `local_0` 在这个模型下是自洽的。要让两个名字对上，必须**跨指令跟踪 SP 的增减**
（pre-index 减、post-index 加）——那是真实状态，不是改名。在有了它之前强行让名字一致，
就是把猜测当事实写进产物。material_3_demo 上 51 个函数是这个形态。

**x64 剩余的 unmapped 是前缀与串操作，而且我上一轮的计数是错的。** 那次枚举按空格截断，
所以报成 `rep` 的 61 条**其实已经是** capstone 合并后的 `rep movsb mem(rdi), mem(rsi)`——
是「一个没认出的操作」，不是「一个裸前缀」。于是 hello_3.13.0 剩余的 142 条构成是：
61 条串操作 + 30 `std` + 30 `cld` + 3 `lock` + 少量 `mul rdx` / `shld` / `shrd` /
`or mem(...), reg` / `bsr`。要还原串操作必须知道**方向标志**：`std; rep movsb; cld` 是反向拷贝的
固定套路，所以单看 `rep movsb` **无法断定**它是向上还是向下拷。渲染成正向 `memcpy` 就是猜；
而把前缀从 `// unmapped:` 改标成 `// note:` 能让数字掉 85% 却信息量为零，同样不做。

## 循环头栈守卫丢失的根因（2026-09-28，已定位、未修）

插桩把问题定死了。在条件分支那条臂上加临时 `DAE_DBG_ARM` 打印，`main` 里 0x4bbdb8 与 0x4bbdc0
两个块都打印了，**唯独 0x4bbdac（守卫所在块）一次都没有**——所以那条 `b.ls` 不是被处理错了，
而是**从未被检查过**。原因在 `Structurer::seq` 的循环头路径：

```rust
if let Some(&(_, exit)) = self.loops.get(&b) {
    let (cond, body_entry) = self.loop_shape(b);
    let mut body = self.body_lines(b);                      // 只取非终止符语句
    body.extend(self.seq(body_entry, Some(b), depth + 1));  // 头块的 terminator 再没人回头看
    out.push(Node::While { cond, body });
    cur = Some(exit);
    continue;                                               // 整个 Branch match 被跳过
}
```

`loop_shape` 假定**循环头的终止分支就是循环条件**。而 Dart 的代码生成里循环头是**栈溢出检查**，
真正的条件在下一个块：

```
块10（循环头）: ldr BARRIER,[THR,#0x48]; cmp SP,BARRIER; b.ls 0x4bbe30   ← 守卫
块11:           cmp r1, #4; b.ge 0x4bbdf0                                ← 循环条件
0x4bbdec:       b 0x4bbdac                                               ← 回边指向循环头
```

于是头块的 `b.ls` 被当成循环条件吸收掉、`body_lines` 只发射那条 `ldr`，守卫就此消失——
而 out-of-line 处理块的 `bl <溢出 stub>` 被内联发射在加载之后（这正是产物里两条语句地址相差
0x64 的原因）。第二个函数 `total` 上形状相同（头 0x4bbe4c、守卫 `b.ls 0x4bbe84`、回边
`b 0x4bbe4c`），且处理块是**尾复制**的（`main` 里有三份：0x4bbe28 / 0x4bbe30 / 0x4bbe38，
都是 `bl 0x4c3c40`）。

**修法必须区分「头块的分支是循环条件」与「头块的分支只是普通守卫」**，而判据现成就有：
`self.loops.get(&b)` 已经给出 exit 块，所以把头块的分支目标与它比一下——相等就是条件，
不等就是守卫、必须在 body 顶部发成 `if`。之所以还没动手：这是全项目**回归风险最高**的一段，
紧接着的注释就记着此前一次过于激进的 `bail` 让 713 个分支失去结构、arm64 ELF 语料的结构化率
从 ~88% 掉到 34%。任何改动都要在**每个语料**上重量结构化率，不能只看门禁。
`stack_check_guards_do_not_regress`（113）与 `empty_if_without_else_does_not_grow`（109）
已经就位，可以抓住「越改越坏」；如果这两个缺陷同源，一次修复应当让**两条棘轮同时下降**。

## 已知缺口（量化过，未修）

* **语句顺序与地址顺序不一致**：21,826 处 = **2.74% 的语句**，波及 **36.1% 的函数**
  （判据：读某寄存器的语句在文本里靠前、定义它的语句在文本里靠后、**且定义的机器地址更早**；
  这样才排除了 live-in 参数——第一版判据把它们也算进去，虚报到 5.52%）。
  **不能用「按地址重排」修**：折叠表达式的正确性依赖它出现在被折叠语句**之前**
  （`rax = rcx + rax // 0x5e3a4` 里的 rcx 是加之前的值），重排会让它变成双重计数。
  要修得二选一——给落地加活跃性分析后抑制冗余落地，或关掉折叠（顺序对了但更啰嗦）。
* **返回值基本没恢复**：裸 `return;` 17,238 vs 带值 `return <expr>;` 790（95.6% 无值）。
  注意这不是「从不恢复」：`classify` 的两个 case 分支都是 `return x0;`，
  统计里大量是 void 函数与尾声。
* **调用不带实参**：所有调用都渲染成 `f()`。实参准备指令现在会落地（见缺陷 1），
  所以读者能从上下文推出参数，但调用行本身仍然没有参数列表。**这不是新发现**——
  下面「已知短板」第 5 条记着它，而且记着**已经试过并撤回**：缺一张经过验证的各 ABI
  破坏寄存器表就算不出真活跃性，硬写实参会把「上一次调用之前写的寄存器」当成本次实参
  （真值语料抓出来过：x0 是 8 条指令、一次调用之前写的）。
* **闭包丢掉所属函数**（`_anon_closure` 而不是
  `_BigIntImpl._cachedDivRemResultValue.<anonymous closure>`）。这是与 blutter 兼容的命名，而且和
  下面那条对象池缺口不同——**数据早就解析进来了**：`ClosureData` 簇在 2.14.4 到 3.13.0 的
  **每一份 profile 里都是 2 个 ref**，2.14.4 的 profile 还给它们标了名（`parent_function` 与
  `closure`），新版本的 profile 读同样两个 ref 但不命名，于是 ref[0] 一直白放着。
  投影之前必须先确认两件事：(a) 各版本的 ref **顺序**一致（只有 2.14.4 写明了——要在自带
  `.symtab` 的语料上验证，那里限定名是独立可知的，判据是 ref[0] 解出一个 Function、ref[1] 解出
  闭包自己的 Function）；(b) 这是一次**有意的全产物重命名**，因为 `_anon_closure` 出现在
  `text/functions.txt`、IDA/r2 脚本和 `frida.js` 里，所有 `regress` 存档都得重切。
  在 `.symtab` 语料上的实测频次：hello_2.15.0 有 40 处、hello_3.13.0 有 26 处，
  全部属于「仅类名/前缀不同」那一类。
* **对象池名字未投影进 IDA/r2 脚本**（blutter 有约 52,700 条 `pp.*`）；数据已在，
  `dae pp` / `dae findrefs` 也能查。

## 这张表反复踩的同一个坑

同一个失效模式已经出现三次，值得直说——**指标看不见它**：指令段定位错了，反编译器读的是
**别的字节**。函数名、结构化率、能不能过分析全都照旧正常（名字来自 Code 对象，合法性只关乎语法）。
唯一能暴露它的是**地址自洽性**（判据：入口像不像序言、直接调用是否落在函数入口上）。

- arm64 `dart compile exe`（尾部内嵌 Mach-O，无符号）——`instr_off = 0`；
- x64 2.12–2.14 / 3.3.4 `dart compile exe`——快照是**另一个 ELF 容器**贴在文件尾部，靠文件末尾
  trailer（`[offset][kAppJITMagicNumber]`）寻址；只看可执行文件自身的符号表就漏了。
  修好之后 `hello_2.13.4` 那 1394 个共同函数的地址**整体偏移一个常量**（`0x462000`）——
  只差这一个基址，别无它因。
- 门禁现在把两种形状都覆盖了：语料里加了 `hello_2.13.4`（尾部内嵌 ELF），序言率下限 0.80
  （错位时实测 51–58%，正确时 91–100%）任一种都会失败。原先那条"末指令是终止符"的判据
  已经退役——它其实在数 x64 的 `int3` 填充，地址全错的语料上它照样报 95.7%。

## 值恢复：对象池常量

`ldr x0, [PP, #0x17f8]` 是**对象池**读取。dae 拿它去对照自己已经解析出来的池条目，于是
字面量直接出现在伪代码里：

```dart
rax = "Hello" /* pp+0x17f8 */;   // 原来是：rax = mem(PP + 0x17f7);
```

两种架构都做过源码对照：应用产物里 `"Testing Sample"`（来自它的 `lib/main.dart`）出现 3 次；
2.15.0 产物里出现 `hello.dart` 的 `"Hello"` 与 `" fib(20)="`。内联字面量条数：应用 1922、
hello_3.13.0 556、hello_2.15.0 579、hello_2.13.4 448、hello_3.3.4 403。

**字符串字面量绝不会被折叠进算术表达式。** 寄存器持有的是池槽的**地址**，字面量是**那个地址上
存的内容**——把后者替换成前者是范畴错误，而 Dart 会直接拒绝：`mem((" fib(20)=") + rdx*8 + 0x17)`
就是 `String + int`，即 `argument_type_not_assignable`。`hello_2.18.1` 那一条全语料唯一的 analyze
错误正是这么来的。字面量仍会出现在载入它的那一行（那才是它该在的地方），
不含算术的引用（如 `call(x0)`）也照旧替换。

这条路踩了三个坑，每个都是"先出了错结果"才发现的：

- **x64 的池指针带 tag**：`[PP + 0x17f7]` 指的是 `0x17f8` 那个条目（tag=1），所以查找
  同时试 `偏移` 与 `偏移+1`——池条目间距 8 字节，两个候选不可能同时是条目。
- **不是所有字符串都认得出来**：`describe_into` 用 cid（93/94）判断字符串，老版本的 cid
  编号不同，于是被描述成**类名** `String`。改成按 ref 直接取（`sref_str`）就与版本无关了。
- **池里混着二进制垃圾**（Unicode 数据表那类）。只有"可打印 ASCII、≤60 字符"才内联，
  且自己做转义（引号/反斜杠/换行）；其余保留内存写法加类型注释。这样也守住了
  "产物零非 ASCII" 的仓库口径。

非字符串条目只给类型注释（`mem(PP, 0x2d8) /* Field */`），不给值——它们不是 Dart 表达式，
硬造一个比什么都不说更糟。

## 字段名：剩下什么，以及两条可证的恢复路径

AOT 把字段名几乎全删了。`Precompiler::DropFields` 只在非 PRODUCT 构建保留字段名，所以发布产物里
只剩**寥寥几十条**：3.13 arm64 样本里 60 条，真实 Flutter 应用里 366 条——而类有几百个、字段有几千个。
其余的名字是真的没了，dae 不去猜。

剩下两条**互相独立**的可证路径：

1. **Field 簇本身**。存活的 `Field` 对象带 `name_`、`owner_` 和 `host_offset_or_field_id_`。最后一个是
   **Smi**，而序列化时 Smis 被并进 *Mint* 簇（`app_snapshot.cc`："Smis are merged into the Mint
   cluster"），所以它的值能从 Mint 的整数里取回来。那个整数就是字段的**字索引**（字 0 = tags；首字段是
   字 1，泛型类里是字 2——字 1 被类型参数占着），于是 `字节偏移 = 字索引 × word_size`。
2. **访问器名**。隐式 getter/setter（`kind` 6/7）的名字就是字段名——私有字段叫 `get:_items`，公开字段
   就叫字段名本身。它们的函数体只碰一个字段，于是"函数体里恰好一处字段形访问"是**可证**条件：偏移来自
   机器码位移、名字来自符号。两处以上访问、或有读不懂形状的访问，这个函数就整条放弃，不猜。
   （`Color.a`、`Paint._data`、`_HitTestResponse.hasPlatformView` 都是这条路来的。）

两条路在中间对上了：3.13 arm64 样本上，访问器路径独立复现了 **41 条中的 40 条** Field 记录，名字与偏移
**全都一致**；同一 SDK 的 x64 产物上 39/39；全语料 **0 冲突**。这是没有源码时能拿到的最强证据——
一侧读的是快照自己的字段表，另一侧读的是机器码加一个函数符号。

偏移换算在接任何一条路之前就先钉死了，用了四个互不相干的角度：

| 核对项 | 证据 |
|---|---|
| `disp + 1 == 字索引 × word_size` | `_FutureListener.get_result` 读 `[x1, #0x17]`（24 = 字 3）；`get_state` `[x2, #0x1f]`（字 4）；`get_callback` `[x1, #0x27]`（字 5）——四个字段四条全中 |
| 字索引 = 声明顺序 | `_Uri.path` 是非泛型类的第 5 个声明字段 → mint 5 → `0x28`；x64 产物里 `_Uri._initializeText` 读 `[rax + 0x27]` 取 `path` |
| 泛型类整体错开一个字 | `_FutureListener`/`_Future` 是泛型：声明在最前的 `_nextListener` 落在字 2；该类的 `fbm`（unboxed 位图）是 `0x10` = bit 4 = `state`，而 `state` 正是第三个声明的字段 |
| tagged 折算 | `Error.get:_stackTrace` 读 `[r1, #7]`、`Error._stackTrace_assign` 写 `[r1, #7]`——字 1 减去 1 位堆对象 tag |

**产物里长什么样。** 恢复出的名字挂在内存访问后面的**归属注释**里，绝不改写访问本身：

```dart
x0 = mem((local_0), 0x17); /* _FutureListener.result (off 0x18) */  // 0x483fb4
```

措辞是刻意选的：注释断言的是「**owner 类**在这个偏移上的字段是它」，对基址不作任何声称——
dae 不跟踪基址的类型，在不知道基址就是接收者的情况下写成 `this.result` 就是编造。aotopsy 敢写
`base.field`，是因为它做全程序类型推断（`typetrack`）；那条路是把差距补完的正解，列在优化清单里。

实测覆盖（改完门禁全绿、`dart analyze` 错误 0）：

| 语料 | Field 记录 | 访问器新增 | 两源一致 | 冲突 | 被注解的访问 |
|---|---|---|---|---|---|
| `sample_arm64`（arm64，3.13） | 60 | 1 | 40 | 0 | 218 |
| `hello_3.13.0.aot`（x64，3.13） | 60 | 0 | 39 | 0 | 152 |
| `T4_blank/libapp.so`（x64，2.12.4） | 34 | 0 | 5 | 0 | 43 |
| Flutter `testing_app`（arm64，3.13） | 366 | 1 | 83 | 0 | 438 |

该沉默的地方就是沉默：字段被删、访问器又被树摇掉的应用类（例如 Flutter 样本里的
`Favorites._items`）拿不到名字，因为快照和符号里都没有。`dae fields <binary>` 只列真恢复出来的东西，
并标出每行的来源（`rec` / `accessor`）；导出产物里同一张表落在 `text/fields.txt`。

`tests/field_names.rs` 把这一切盯住：每条语料的记录/一致数下限、**零冲突**、探针字段必须落在确切偏移上，
以及最能抓编造的一条——产物里出现的每个 `/* 类.字段 (off 0x..) */` 都必须在恢复表里有同名同偏移的条目，
且偏移按 `word_size` 对齐。

## 又两个坑，都是加语料加出来的

新增一条 **arm64 ELF** 语料（`testing/variants/h212keep_linux_arm64.exe`——门禁语料里唯一缺的
平台/容器组合）之后，结构化率从 ~88% 掉到 **34%**，并冒出 55 条 `dart analyze` 错误。三个独立原因：

1. **没有落空后继**：条件分支落在函数**最后一个块**时，它后面没有后继——因为表给的函数尺寸就在
   分支处结束了。结构化器把"落空后继未知"当成了"目标越界"直接放弃，在这条语料上白白损失 713 个
   分支。现在把目标支结构成 `if (…) { … }` 并收尾：**34% → 89%**。
2. **嵌套无上限**：`seq` 每遇一个菱形就往下递归一层，1608 个块的函数能钻到约 50 层——产物变成
   阶梯状的 `}`，Dart 解析器直接报 `stack_overflow`（嵌套过深）。现在封顶 10 层，更深的区域
   平铺发射并如实写 `gotoLabel` + 函数头 `NOTE`。
3. **是门禁的 bug，不是产物的 bug**：池里内联出的字符串字面量本身是 `}`（`BARRIER = "}" /* pp+0x2410 */`），
   把形态门禁的花括号计数带偏了。语句结束判据早就屏蔽了字面量，花括号计数没有——改正门禁一侧。

同一文件上再对一次 aotopsy：两个工具都能读的语料上 dae 结构化 89%、aotopsy 63%，
`dart analyze` 错误 0 vs 约 7 万，见 [`COMPARISON.zh.md`](COMPARISON.zh.md)。

## 已知短板（优化清单）

1. 共享尾块与不可归约循环：**前向**跳进已发射块的用尾复制处理（`dup_tail` 把那段直线代码再写一遍，
   打 `duplicated tail` 注释；限 16 块 / 每函数 256 条语句），真实应用里救回 66 个函数。
   **回头**跳到非循环头块的属于真正的不可归约循环（实测 715 处，`is_loop_header=false`）——
   Dart 没有 goto 就表达不了，保留 `gotoLabel` 与函数头 `NOTE` 标记。
2. `unmapped` 现在多数语料只剩个位数（真实应用 3 行、3.3.4/3.4.0 各 1 行），靠最后一轮 lift
   （`xchg`/`idiv`/`sbc`/`adc`/`umulh`/`clz`/`stxr`/`br`/`msub`/`fcvtm*`、SSE 搬移与转换），
   机器专有的操作写成声明的占位函数调用（`Op::Helper`）而不再落到 `// unmapped:`。
   `csel` 的条件现在会跟着上一条 `cmp` 折出真条件（`(x0 == x1) ? a : b`，不再是 `(hi) ? a : b`）。
3. **老旧 x64 可执行文件（2.12–2.14、3.3.4）从来就不弱**——64–69% 是读错字节说出来的数字。
   地址修好后它们稳在 **87–91% 结构化、21–231 行未映射**，与其它版本同一档。真正剩下的问题：
   **内存目的地的** `add`/`or`/`sub`/`inc`/`dec`（`add byte ptr [rax], 8`），以及表给的 code size
   把函数截在最后一个分支目标之前造成的 `.byte` 段。
4. 类型恢复只做了一半：池**值**已解析、字段名也归了属（都在上面），但**基址的类型**没跟踪，
   所以访问写成 `mem(base, disp) /* 类.字段 (off 0x..) */` 而不是 `base.field`。补这一步和
   aotopsy 的 `typetrack` 是同一件事：从调用点、池条目和接收者槽做全程序传播。
   局部变量与参数仍是 `dynamic`。
5. **调用点不显示实参**，于是调用方准备的寄存器看起来像死写：`x1 = NULL; x2 = 6; sub_0x2bb1d0();`
   ——这是 `unused_local_variable` 警告的主要来源（整个 Flutter 构建 10,023 条，160 行的真值语料
   1,475 条）。写成 `sub_0x2bb1d0(x0, x1, x2)` 看着 trivial，但**现在还不诚实**：某个实参寄存器可能是在
   一次**中间调用之前**写的（Dart 的栈溢出 stub 会保留接收者，所以下一个 `bl` 处 x0 仍有效），而 dae
   手里没有经过验证的**各 ABI 破坏寄存器表**——有了它就能算真正的活跃性，再把实参写出来。
   已经试过并撤回，正是被真值语料抓出来的（x0 是 8 条指令、一次调用之前写的）。
6. 前导声明是每文件机械生成的；更聪明的做法是只声明用到的，并给占位函数真实签名。
7. **语句顺序与地址顺序不一致**（2026-09-28 源码对照量出来的）：21 826 处 = 2.74% 的语句、
   波及 36.1% 的函数。**不能靠按地址重排修**——折叠表达式的正确性依赖它出现在被折叠语句之前。
   详见上面「已知缺口」。
8. **返回值基本没恢复**：裸 `return;` 占 95.6%（17 238 vs 790）。不是「从不恢复」
   （`classify` 的两个 case 分支都是 `return x0;`），统计被 void 函数与尾声主导。
